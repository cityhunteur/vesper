| TD-038 | Narrowed by GH #150 (launcher FSEvents watcher plus guest replay; council rework on 2026-11-11): host edits on watched read-write shares reach containers as `IN_MODIFY`. GH #29 item 3 was ticked on 2026-11-11 as a qualified tick, with the residuals in this row (owner's decision of 2026-11-10, decision log D-003). Residuals. Events: no `IN_CREATE`, `IN_DELETE`, `IN_MOVED_FROM`/`IN_MOVED_TO` or `IN_CLOSE_WRITE` for host changes (deletes and renames show as `IN_MODIFY` on the parent directory); a host `chmod`-only change never arrives as `IN_ATTRIB` (it is dropped, or shows as `IN_MODIFY` when the path was not sent before); a container's own write on a watched share gives one extra `IN_MODIFY`; a watch on a single file does not follow a host atomic save; `IN_CREATE`-driven recursive watchers (`inotifywait -r`) do not follow directories created on the host. Silent: deletes, renames away and directory deletes directly in a share's root directory; every edit on a read-only share. Limits: after FSEvents drops events the rescan visits at most 50,000 entries and sends only those modified in the last 60 s, so a tree moved into a share with old mtimes is not signalled; the queue holds 100,000 lines and the oldest are dropped beyond that; the lines already written when the sink handler dies (normally one batch) may be lost; an edit that keeps both mtime (ns) and size is taken for an echo and not sent. Untested: a physical external disk, a network volume, and file systems with coarse timestamps such as exFAT under rapid same-size edits (APFS, case-sensitive APFS and exFAT disk images pass the watcher self-test).
